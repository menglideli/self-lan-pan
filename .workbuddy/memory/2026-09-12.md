### 探针发现的第 3 个真 bug（不是用户报的）

`PolicyUpdate` 沿用了新建用的 `policyIn`，而它把 `name` 与 `type` 都标了 `binding:"required"` —— 编辑框不会再送 `type`，于是任何"只改挂载目录"的请求**先被判「参数错误」**，新加的目录存在性校验根本进不去。已拆出独立的 `policyPatchIn`（`name`/`type` 均可选，`name` 留空保持原值）。

### 「测通」的语义修正

原 `checkPolicy` 直接调 `fscore.NewLocal` —— 而它内部是 `os.MkdirAll`，会把**已经被删掉的挂载目录悄悄重建出来**，然后报「目录可读」= **验证手段本身在制造假通过**。新的 `handler/policycheck.go` 先 `os.Stat` 再 `List`。

### 本轮踩到的坑

- **「同一文件并行下发多个 Edit 会丢改动」又中招，而且这次最隐蔽**：一条消息里给 `probe-webdav.mjs` 发 5 处改动**实际落盘 0 处**，`probe-m3u8.mjs` 发 4 处只落 2 处（第 2、4 处），`ui.mjs` 发 2 处只落 1 处，`README.md` 发 4 处只落 1 处。`Edit` **全部返回 `Successfully edited`**，而回归跑出来的 FAIL 文案**正是已经删掉的那几句** —— 一度以为是自己的改动思路错了，实际是改动没落盘。→ **同一文件必须串行下发，改完 grep 复核目标行**。
- **宽断言等于没断言**：`code !== 0` 在真实系统里几乎不会失败（总有别的校验先拦住）。断言要认"为什么失败"。
- **PowerShell `Start-Process` 在本机报 `ArgumentException`**：环境里同时存在 `HTTPS_PROXY` 与 `https_proxy` 两个大小写不同的同名键，.NET 字典大小写不敏感直接抛错。改用 `& $exe … | Out-String` + `[IO.File]::WriteAllText(..., UTF8 无 BOM)` 落盘，中文不乱码。
- PowerShell 5.1 的 `Tee-Object` 会把 node 的 UTF-8 输出按 ANSI 解码 → 结果文件里中文全是乱码。同上改用 `[IO.File]::WriteAllText` 后干净。
- `probe-webdav.mjs` 里有一处旧断言把长命名的 `我的电影` 挂载路径写死成 `/dav/我的电影-m1/`：`genPolicyLetter()` 对纯中文名生成 `M`/`M1`，所以实际路径段是 `我的电影-m1` —— 断言与实现一致，未改。

## 运维边界审计（318 条断言全绿之后做的补课）

功能探针全绿 ≠ 系统安全。这轮专门查「探针覆盖不到的运维边界」，全部以代码为证（非推测）：

| # | 隐患 | 证据 | 触发场景 |
| --- | --- | --- | --- |
| 1 | **WebDAV 用错凭据能把管理员反锁** | `auth.go:75` 锁定键 = `ClientIP + "|" + 用户名`；`webdav.go:476-503` 的 Basic Auth **复用同一套 `loginLocked`/`loginFail`**；全项目**无解锁入口**（只能重启进程清内存计数） | 改了密码但 Windows 映射驱动器 / 手机 WebDAV App 仍在后台重试旧凭据 → 每 15 分钟循环锁一次 → 网页登录一律 4291，用户会以为服务坏了 |
| 2 | **初始 admin 密码只打印一次，丢了只能删库** | `model.go:398` `首次部署：初始管理员密码为 %s（仅本次日志输出）`；`start.bat` 仅双击跑控制台 | 首次启动窗口没截到 / 中文乱码 / 提前关了 → 密码永久丢失；恢复手段只剩删 `cloudpan.db`，连带任务历史 / 回收站索引 / 哈希库 / 审计全没 |
| 3 | **挂载根可以包含 DataDir → 在网盘里删掉系统自己** | 全项目**无任何「挂载根 vs 数据目录」包含关系校验** | 把 `D:\` 当挂载根且 `CP_DATA` 也在 D 盘 → 网盘里直接看到 `data/`（db + `secret.key` + 回收站），右键删除 = 系统自杀 |
| 4 | **备份对象是 4 个文件不是 1 个** | `model.go:368` `journal_mode(WAL)`；`config.go:42` 密钥持久化在 `DataDir/secret.key` | 只拷 `cloudpan.db` → WAL 里最近事务丢失；漏 `secret.key` → 全部签名/会话失效；漏 `recycle/` → 回收站变空 |

| 6 | **数据目录 = 启动时 cwd 下的 `./data`** | `config.go:24-27` `dataDir = "./data"` → `filepath.Abs` | `start.bat` 用 `cd /d "%~dp0server"` 挡着；一旦改用计划任务 / Windows 服务 / 快捷方式启动 → 新建**空 data + 新 `secret.key`** → 「文件全没了」+ 旧直链全失效。仓库里的 `server\data` 即此条实证 |
| 7 | **全站 HTTP 明文，WebDAV Basic 每请求重发密码** | `main.go:91` 只有 `http.Server`，无 TLS；`main.go:82` 监听 `:18322`（0.0.0.0 全网卡） | 同局域网 ARP 欺骗 / 镜像口即可拿到 admin 明文密码。**绝不要为远程访问做端口转发** |

## 批次 12：跨平台支持与打包运行说明（同日）

用户问：「全平台是否支持？Windows 目前 100% 可以，但是 iOS 和 Linux 呢？Go 是跨平台的应该可以，不过你要看看内部一些核心 IO 是否也支持；支持的话把它加上，还要 README 加上如何打包运行就行。不用考虑 NAS，那些都自带系统，我们这个针对个人。」

### 实测结论（不是"应该可以"）

七个目标在 Windows 上以 `CGO_ENABLED=0` 交叉编译，**全部 exit 0**，并**读产物文件头核对**（不靠文件名）：

| 目标 | 文件头 | 架构 | 大小 |
| --- | --- | --- | --- |
| windows/amd64 | PE/COFF | x86-64 | 61.2 MB |
| windows/arm64 | PE/COFF | ARM64 | 56.8 MB |
| linux/amd64 | ELF（ET_EXEC 静态） | x86-64 | 60.6 MB |
| linux/arm64 | ELF（ET_EXEC 静态） | AArch64 | 56.8 MB |
| linux/arm v7 | ELF（ET_EXEC 静态） | ARM 32-bit | 57.2 MB |
| darwin/amd64 | Mach-O | x86_64 | 62.1 MB |
| darwin/arm64 | Mach-O | arm64 | 58.7 MB |

`linux/arm`、`darwin/amd64`、`darwin/arm64` 另经 `go vet ./...` 通过。三个 Linux 产物是 **ET_EXEC 静态可执行**，不依赖 glibc/musl，换发行版直接跑。

### 为什么能跨平台（逐项核过，非推测）

- SQLite 用 `glebarez/sqlite` → `modernc.org/sqlite` **纯 Go**，`CGO_ENABLED=0` 可用 —— 这是能出静态二进制的前提
- `anacrolix/torrent` 的 `go-libutp` 在无 CGO 时有非 CGO 路径
- `gopsutil` 分平台实现，且**每项调用都有 `err == nil` 守卫**，取不到就跳过，Linux 上不白屏
- 源码 **0 处** `syscall`、**0 处** `//go:build`、**0 处** `os/user`
- `go.mod` 里 `creack/pty` 是**残留声明、源码从未 import**（终端功能早已裁剪），不影响任何平台
- 已有 `runtime.GOOS` 三处分支本就是跨平台写法：绝对路径/反斜杠校验（`admin.go`/`localdir.go`）、Windows 文件名规范化（`sanitize.go`）、可浏览根列表（Windows 盘符 ↔ `/`）

### iOS 的准确定位（README 必须写明白，不能含糊成"支持 iOS"）

- **服务端跑不了**：Go 编到 iOS 需要 `CGO_ENABLED=1` + Xcode，产物只能是必须嵌入 App 的 framework（gomobile）；更根本的是 iOS 不允许 App 后台常驻并监听端口。**换任何语言都一样。**
- **客户端可以**：Safari 网页版；或第三方 WebDAV App（Documents / nPlayer）。**iOS 自带「文件」App 不直接支持 WebDAV。**

### 真正的坑在仓库层（读 Go 代码一万遍也看不出来）

| 缺陷 | 后果 |
| --- | --- |
| `build.sh` 在 git 里是 `100644`（无执行位） | macOS / Linux 上 `./build.sh` → `Permission denied`。已 `git update-index --chmod=+x` 改为 `100755`，并新增同样带执行位的 `start.sh` |
| `.gitattributes` 只有 `* text=auto` | 管住了提交方向、没管 checkout 方向；而 `core.autocrlf` 是**各人本地配置、仓库层面管不住**。只要有人在 Linux（`autocrlf=false`）提交 CRLF 的 `.sh`，此后所有人 clone 都报 `/bin/bash^M: bad interpreter`。已补 `*.sh text eol=lf`、`*.bat`/`*.cmd text eol=crlf` |
| 前端文案写死 Windows | 管理台 `如 E:\媒体\电影`、文件管理器 `点进下面任意一个盘符 / 目录` —— 非 Windows 用户看着莫名其妙，已改成并列给出两个平台示例 |

### 环境坑（两次都长得像代码缺陷，务必先排除环境）

- `open ...\_pkg_.a: Access is denied` → **沙箱不允许 Go 工具链的子进程写指定路径**，而 PowerShell 自己写同一目录却是成功的。**"我能写" ≠ "我拉起的子进程能写"。**
- `resize output file failed: There is not enough space on the disk` → 本机 **C 盘只剩 0.2 GB**（Go 构建缓存占 2.86 GB）。`go clean -cache` 释放约 2.9 GB 后恢复（注意 `Get-PSDrive` 的读数有延迟，别在下一次调用里立刻判"清理无效"）。
- **教训**：若直接下结论"ARM / macOS 编不过"，就是把自己的环境问题写成项目缺陷。
