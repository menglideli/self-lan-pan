### 验证方法上的一个重要教训（值得单独记）

**反向变异验证是唯一能抓出"空转断言"的手段。** 本批第一次做变异时，`ui.mjs` 里那条
"根视图无盘符"的断言**仍然 PASS** —— 因为它写在 Node 侧却多转义了一层：
`/\\([A-Z0-9]{1,4}\\)$/` 实际匹配的是"反斜杠+括号"，正常字符串永远对不上，
`every(...)` 恒为 true。修成 `/\([A-Z0-9]{1,4}\)$/` 后再跑变异，立刻 FAIL。

规律：**写进 `evalOr` 模板字符串的正则要双反斜杠，写在 Node 侧的要单反斜杠**，
两者混用极易出事。新写的每条断言都要能回答"怎样才会 FAIL"。

### 本轮新踩的坑

- **`dto.Fail(c, 400, msg)` 返回的是 HTTP 200 + body `{code:400}`**（只有 `FailHTTP` 才改状态码）。
  三处断言误用 `r.status === 400` 导致误判，改为断言 `r.json.code`。
- **上一轮测试的副作用会污染下一轮**：旧 exe 的 `MkdirAll` 在 `D:\` 建出的目录，
  让下一轮"拒绝不存在路径"的断言结果失真。对策：测试用的"不该存在的路径"随机化，
  并额外断言 `!fs.existsSync(p)`（副作用未发生）。
- **`.git/index.lock` 残留**：某次 git 调用被打断后留下 lock，后续 `add`/`commit` 全报
  `Another git process seems to be running`。确认无 git 进程后直接删该文件即可。
