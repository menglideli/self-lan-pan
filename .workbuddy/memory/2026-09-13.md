### 两个关键设计点（别改回去）
1. **`out/` 故意不清空**。用户可能已经把 out/ 当部署目录跑过，`out/data` 就是他真实的数据；
   沿用手感的 `rmdir /s /q out` 会让"重新构建"变成"删数据"。现在只覆盖那 5 个交付文件，
   检测到 `out\data` 还会打印一行提示。
2. **交付包里的 `.bat`/`.txt` 必须收尾转 CRLF**。`.gitattributes` 的 `eol=crlf` **只在 checkout
   那一刻生效**，之后任何重写文件的工具（编辑器、Write）都会把它变回 LF，`copy` 出去就是 LF 版。
   实测本机 cmd 跑 LF 版的多行 `if` 块**没崩**，但那是运气不是保证。
   实现：`build.bat` 内联 PowerShell（全单引号，规避 cmd 引号地狱）；`build.sh` 用 `awk`。

## 批次 14：远程下载缓存治理 + BT 三个真缺陷

用户需求原话：
> 我发现还有一个问题，就是远程下载 有几个问题BT下载以后其实都下好了 文件名字不对 没有copy过去
> 而是保留了缓存 没有删除，删除也不会删除缓存 这样会越来越大 ，其他m3u8和普通下载缓存完成以后
> copy到模板文件但是目录下面还是有缓存 导致越来越大 先解决这几个问题 然后重新打包一下
> 为了快速使用 这个很有必要操作

拆成 5 条：BT 没进网盘 / BT 缓存不删 / BT 文件名不对 / m3u8 与直链缓存残留 / 删除任务不清缓存。

### 第一步：先证伪，别急着改

三处 `defer os.Remove`/`os.RemoveAll` **本来就都在**，与用户"缓存没删"的反馈矛盾。
写探针实测（`probe-offline` / `probe-cache`）：

| 场景 | 结果 |
| --- | --- |
| 取消直链下载 | `cp_offline_<id>.tmp`（3.25MB）**被清** ✅ |
| 下载失败（404） | 无残留 ✅ |
| 取消 BT 任务 | `bt_tmp/<id>/` **被清** ✅ |
| **手工放残留 + 完整重启** | `bt_tmp/99999/`（0.5MB）与 `%TEMP%/cp_offline_88888.tmp`（0.25MB）**双双存活** ❌ |

并在用户真实机器的 `%TEMP%` 里找到 2 个 `cp_offline_*.tmp`（2026-09-12，2769B / 646B）。

⇒ **根因不是"没写清理"，而是"异常终止后的残留没人回收"**（启动不清、运行期不清）。
`defer` 只在执行体正常返回时执行；强杀 / 断电 / 崩溃全都不执行。

### 第二步：BT 侧另外凿出 3 个真缺陷

用本机做种（`btseed`）+ 极简 tracker（`bttracker`）做真实传输才测出来的：

1. **固定监听端口 42069** → 第二个并发 BT 任务必失败
   （实测 `listen tcp4 :42069: bind: Only one usage of each socket address`）
2. **进度循环没有停滞超时** → 拿不到 peer 时**永远卡 processing 0%**（实测 90 秒仍在处理中），`bt_tmp/<id>` 一直占盘
3. **`Delete` 只删 DB 记录、完全不碰磁盘**

另确认**不属于本仓库的问题**：`.torrent` 加载后 tracker announce 从未发出，最小复现程序 `btmin` 同样如此
→ 库/环境行为。对外别承诺"BT 一定能下动"。

### 第三步：改了什么

| 文件 | 改动 |
| --- | --- |
| `handler/cache.go`（**新建**） | 三处缓存路径的**唯一事实来源** + 统一清扫 |
| `tasks.go` | `InitTaskPool(svc, btDir, zipTmp)` 三参数（原先 `Zips` 从未赋值）；启动时与每 6h 各清一次；`run()` 三分支 + `Cancel` + `Delete` 各清一次 |
| `bt.go` | 端口按任务散列 `42300 + id%500`；`btStallTimeout = 5min`；导入路径 `resolvePhys()` 三种布局兜底 |
| `m3u8.go` | 临时目录 `m3u8-<随机>` → **`m3u8-<taskID>`**（可精确定位） |
| `main.go` | 传第三个参数 `cfg.Sub("ziptmp")` |

**关键设计**：清扫只认本程序自己的命名规则（`bt_tmp` 下纯数字 / `ziptmp` 下 `m3u8-` 前缀 /
`%TEMP%` 下 `cp_offline_*.tmp`），且用**整棵树最新 mtime** 判"1 分钟内写过"的宽限——
目录自身 mtime 在写文件时不更新，拿它当判据会误删正在写的任务。

### 差点让验证失效的两点

1. **fixture 回溯 mtime 只回溯了目录、没回溯目录里的文件** → 清扫器（按整棵树最新 mtime 判活跃）
   正确跳过，被我误读成"清扫没生效"，差点去改一段本来正确的代码。
   **教训：fixture 造得不对，会把"正确行为"报成 bug。**
2. **变异版探针生成失败（`MODULE_NOT_FOUND`）**：用内联 `node -e` 拼引号把内容写坏了。
   改用 `String.split(...).join(...)` 重写成功。
   **教训：内联 heredoc/转义写生成器很脆，能落文件就落文件。**
