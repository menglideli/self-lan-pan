## 批次 15：分享审计与「卸载挂载」解耦

用户需求原话：
> 分享审计我发现有问题，已经过期的分享链接还在挂在分享审计里面 然后我取消挂载取消不了
> 这个问题有点大 应该到期至少不挂载有个记录就行 然后能我卸载也正常 先调整排查

### 先复现（用真实库副本，原始数据只读）

把 `server/data` 复制到 `%TEMP%` 再启动。**登录问题**：用户改过密码，不知道明文 →
在一处临时环境里用 API 把密码改成已知值、取出那段 bcrypt 哈希，再写进副本库（不猜不重置）。

真实库现状：
| 项 | 值 |
| --- | --- |
| `shares` | **只有 1 条**：id=1、policy_id=1（百灵鸟）、`/理光驱动.rar`、`expires_at=2026-09-12`（已过期） |
| `policies` | 1 百灵鸟、2 返利一体化 |
| `GET /api/admin/shares` | 照列出来，**无任何"已失效"标识** |
| `DELETE /api/admin/policies/1` | **400 存在关联分享，请先取消** |
| `DELETE /api/admin/shares/1` | `code:0` —— **取消本身是通的** |

### 根因

`PolicyDelete` 用 `Count` 统计**全部分享**（含早已过期的）→ 一条很久前过期、用户想不起来的
分享把挂载**永久锁死**；审计列表又不给状态提示 → 两条合起来才是"这个问题有点大"。
（用户说的"取消挂载取消不了"，实测卡点是**卸载**，不是取消分享。）

### 关键设计：判据统一

`model/model.go` 新增 `Share.State()` → `active`/`expired`/`exhausted`；
`Available()` 改为 `State()=="active"`；新增**同义 SQL 条件** `ShareActiveCond`
`= "(expires_at IS NULL OR expires_at > ?) AND remain_downloads <> 0"`。
**早先"能不能访问"与"能不能卸载"是两套判据，后者更宽 —— 宽出来的部分就是 bug。**

### 改动清单

| 文件 | 改动 |
| --- | --- |
| `model/model.go` | `State()` / 三常量 / `ShareActiveCond`；`Available()` 委托 |
| `handler/admin.go` | `PolicyDelete` 只统计生效分享（放行已失效，**记录不删**）；`ShareAudit` 返回 `state`/`available`/`remainDownloads` |
| `handler/share.go` | `Mine` 不再直出 `model.Share`，改出 `hasPassword`/`state`/`available` |
| `AdminConsole.vue` | 状态列 + `生效中 N · 已失效 M` 计数 + 失效行 `opacity:.55` + 失效行「清记录」 |
| `SettingsApp.vue` | 提取码列改 `hasPassword`；加状态列；去掉恒不成立的"提取码见分享设置" |

**顺手修掉的真 bug**：`Mine` 原先直出 `model.Share`，而 `PasswordHash` 带 `json:"-"`，
前端读 `passwordHash` 恒 `undefined` → 有密码的分享**恒显示「公开」**。
（同类陷阱：任何带 `json:"-"` 的字段都不能指望下发到前端。）

### 差点让验证失效的点

`probe-real-unmount.mjs` 里原有一条**修复前写的反向断言**「列表里没有任何已失效标识」，
修复后必然变红。**只看 `FAIL=1` 就去改代码，会把刚修好的改回去。**
→ 反向断言在修复完成后必须逐条复核语义，不能当回归失败处理。
